## S01 已转录、翻译的任务开始配音后，阶段暂时退回转录

优先级：高。状态：已定位分支误判，最小输入验证成立；尚未修复。

证据：`app/core/gpu_lifecycle.py` 的模型切换事件包含 `status: switching_model`、`gpu_stage: tts`，但不包含 `pipeline_status`。`app/frontend/src/hooks/useTaskProcessing.js` 在通用阶段解析前，依据 `STANDALONE_TRANSCRIPTION_STATUSES` 把该事件强制归到 transcribe，忽略 gpu_stage。

最小验证：输入 `{status:'switching_model', gpu_stage:'tts'}`，`stageIdForEvent` 的结果是 dub，但现有提前分支的条件同时为真。后续 dubbing 事件到达才把阶段改回 dub，符合图 1→3 的现象。此证据不表示后台重新执行了 ASR。

待修复：阶段信息优先级一致化；明确区分独立转录与流水线模型准备事件。

验收：已有转录、翻译开始配音；tts 准备/排队/模型切换；真正 ASR 准备；SSE 重连与任务切换，均不误归阶段。

## S02 中断后重新开始，前端仍失败但后台继续执行

优先级：高。状态：已收到完整日志和最终 history；确认后台最终成功及重试前订阅先关闭，旧快照竞态仍需受控复现确认。

证据：前端 run() 在 video-plan 预检前设置 running=true 并建立 SSE。此时服务端可能仍保存上一次 failed 状态，初始快照会触发失败分支并停止前端订阅；异步预检/启动请求未因此取消，随后仍可能成功发起新任务。`startDubbing` 成功后只更新 message，不一定恢复已被旧快照撤销的 running/status。后台启动接口也未在开始预检前建立新的运行代次标识。

最小核对：旧 failed 记录的恢复结果为 running=false/status=failed。仍需模拟完整时序，区分旧快照、新任务失败及工作线程继续执行等其他可能；不能仅凭该恢复结果宣称完整复现。

截图 5 单独不足以证明流水线完成；2026-10-17 新提供的 history 已补足该证据。任务 e4d28fb5 的最终 status、pipeline_status、dubbing_status、burn_status 均为 completed，outputs_stale=false，最终输出路径已保存。

新增时序证据（日志原记录时间，2026-10-16）：

- 19:11:58—19:11:59：第一次配音因 180 秒 TTS 合成超时而真实失败，不能误判为纯 UI 错误。
- 19:33:55.185：SSE 连接关闭；19:33:56.758：后台开始下一轮配音；期间启动请求为 200。另一次启动为 409，表明后台仍在执行，不能由按钮可点推断空闲。
- 20:18:03—20:18:04：第二轮也因 180 秒合成超时真实失败。
- 22:42:04.915：SSE 再次先关闭；22:42:06.099：第三轮后台开始配音。
- 22:57:14.879：第三轮复用 15 条自然语句、重新合成 19 条，共 34 条；22:57:27.867 配音完成；22:58:04.903 烧录完成；最终 history 证实整条流水线已成功。

结论：这次既有真实合成失败，也有前端跟踪与重试不同步的证据。SSE 关闭早于新一轮开始与旧失败快照路径吻合，但日志没有记录每条 SSE 消息内容，尚不能直接证明关闭的唯一触发条件。后续修复必须同时保护真实错误显示与新运行跟踪。180 秒超时及失败后的音色回退另作为关联稳定性问题保留，不在本轮擅自延长超时或更换音色。

待修复方向：请求/运行代次与服务端权威状态对齐；过滤旧终态；新请求被接收后必须恢复跟踪；断线/失败后可重新校准状态。不能只改颜色、隐藏错误。

验收：旧失败快照在预检期间到达、旧完成快照、409 已运行、快速断线重连、重启恢复、真实新运行失败；验证按钮锁定、前端阶段和后端状态一致。

## U02 仅烧录字幕缺少视频输出策略

## U03 清空字幕后无法重新输入或添加

优先级：高。状态：清空后无法重新编辑的界面原因已定位；插入新行是另一个明确功能缺口。

证据：VideoPreview 的 source/target 文本通过 span 点击进入编辑；`text || ''` 使清空后的 span 无可见内容和有效点击面积。现有接口是按 index 编辑已有行，并无新增字幕行入口。

待处理：首先提供空单元格始终可见且键盘可达的编辑入口；再评估真正新增/删除行与时间输入、原文译文映射、导出和配音缓存的同步。不能把“清空文本”误当作结构性删除行。

验收：清空源文/译文、保存、再次输入、刷新后重编辑；如支持插行，确认所有语言、行号、时间轴与缓存正确映射。

## U04 编辑译文后刷新，原文偶尔为空

优先级：高。状态：待复现，未发现足以证明原文文件被改空的证据。

证据：VideoPreview 在任务切换清空 sourceSegments；源文 fetch 不检查 res.ok，失败仅 console.error，界面无重试或明确失败提示；译文加载独立，存在“仅源文加载失败”的表现路径。当前编辑接口的 target_text 分支不应直接覆盖原文，不能据此认定数据丢失。

排查：刷新前后源 JSON 是否仍有内容；源地址、HTTP 状态、JSON 解析、任务路径序列化、并发加载取消、原文显示开关。不要覆盖现场文件。

验收：源请求一次失败后恢复、任务快速切换、语言切换、刷新、编辑后刷新；明确区分加载失败、隐藏原文与真实空记录。

## U05 导出预览音频、视频无法拖动进度

优先级：中。状态：待媒体与 HTTP 实测。

证据：ExportPanel 使用原生 audio/video，路径为 `/static/output/`；输出由 StaticFiles 提供，不走上传视频的自定义 `/video/` Range 路由。但这不意味着 StaticFiles 不支持 Range：必须核实包内版本、206/Content-Range/Content-Length、媒体时长与索引，以及请求是否因刷新重新挂载而复位。

验收：目标包内原 WAV、MP4；首次与缓冲后的 seek；实际 currentTime 保持；合法/后缀/非法 Range；下载内容和预览一致。暂不认定为单纯前端控件问题。

## U06 有译文错位提示时仍继续配音

优先级：高。状态：缺少审核暂停机制已确认，尚未修复。

证据：translation API 记录 alignment_review_rows 和 check_incomplete；PipelineService 在翻译后直接导出并开始配音，无翻译审核等待状态。

用户最初提出两种方案；2026-10-17 已明确选择：每次翻译完成都暂停，手动继续。无需以错位提示作为暂停条件。确认绑定译文版本，刷新/重启恢复等待，同一已确认版本继续时不重复阻塞。该选择已写入处理计划，应用行为尚未修改。

待设计：持久化人工审核状态、继续/取消、刷新恢复、修改后复核、继续时读取最新译文并使旧音频失效。提示不等于确定翻译错误，不应静默改写。

验收：有可疑行、审核不可用、无可疑行、修改后继续、直接确认继续、刷新/重启恢复、用户取消。字幕导出与配音继续需分别定义。

## U07 两轮精简仍不满足后缺少人工处理入口

优先级：高。状态：现有行为已确认，尚未修复。

证据：PipelineService 捕获 DubbingCompressionRequired，在 attempts<2 时保存 segment_indices 并等待确认；达到 2 次后转为 RuntimeError，失败处理会把 compression_request 清空，界面缺少可定位的问题列表和继续入口。

待设计：保留原字幕行号、分组映射、测量时长和超出量；转为需要人工编辑的可恢复状态。编辑确认后复测并选择性复用未改音频，不自动无限压缩，不静默截断对白。

用户补充要求：在字幕预览中高亮问题句子，提供原字幕行号定位；问题配音组涉及多行时标记对应的所有原行，不混用组号与字幕行号。标识时长/同步问题的原因；刷新后保留，重新测量通过才清除。复用现有主按钮继续，尽量不新增按钮。

验收：到达两次后仍可定位问题；修改后继续；刷新/重启保留；未修改仍不足；更换音色或退出；无关片段缓存不丢失。

## U08 时间轴重叠，预览看似正常而烧录叠字；自动处理与配音影响

优先级：高。状态：预览/烧录差异已定位并最小验证；大量重叠来源需用户实际 JSON 定位。

证据：VideoPreview 使用 find()，同一时刻只取第一条源文和第一条译文；formatter_service 为每一行原样输出 ASS Dialogue，且使用同一 `\\an2\\pos`。时间重叠时，多行字幕会同时落在同一位置。

最小验证：两行时间 [0,3]、[2,4]；t=2.5 同时存在 2 行，预览规则只选 First，ASS 仍输出 2 个事件。预览不叠字不能证明时间轴没有重叠。

重叠原因待区分：Whisper 解码返回、应用长音频重叠分块去重不足、人工修改、真实多人同时说话，以及源译文时间不一致。旧边界修复只裁剪媒体总时长，未消除内部重叠。

用户 2026-10-17 补充：此前遇到大量重叠提示后，都会先手动逐条修正再继续，因此没有保留到成品阶段的实际叠字。核心诉求是减少每次人工改时间轴的成本，不是再增加一次强制人工检查。

资料核对：本次新增完整日志及 history 属于 e4d28fb5（46 条字幕，配音合并为 34 条自然语句）。目录内唯一转录 JSON 仍属于旧任务 7841a56e，共 42 行；按当前 1ms 容差规则检测为 0 对重叠。不能用这个旧文件的检测结果反驳用户反复遇到重叠，也不能据此推断新任务的重叠规模或根因。当前无修改前的重叠源/译文 JSON，无需用户为留现场而重做已经完成的人工修改。

配音并非一定会直接混音重叠：dubbing_service 会分组并进行顺序调度，但异常时间仍可能影响分组、可用时长、同步偏差和精简判断，不能视为仅视觉问题。

自动处理建议：转录后先保留未经修改的原始结果；对高置信的重复/小边界冲突自动修正，并提供汇总及撤销，不要求用户逐条确认安全项；只把无法安全判断的严重冲突交给人工。重复片段合并、极小边界重叠与大范围语义重叠分开处理，具体阈值和算法尚未决定。真正并行对白不能简单裁掉或丢弃；原文、所有译文、导出、配音必须使用一致的生效时间轴。策略需用真实样本验证，不直接批量覆盖。

验收：嵌套重叠、多个重叠、乱序、相同时间、零长度、正常相邻、多人对白；保证正时长、无丢行、同步源译文、可回滚、配音同步与缓存失效正确。
