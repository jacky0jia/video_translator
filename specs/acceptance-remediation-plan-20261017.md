# 2026-10-17 验收问题检查与处理计划

状态：计划与扩大范围检查，不是修复完成报告。覆盖 `acceptance-issues-20261017.md` 的 S01、S02、U01—U08，并扩展前后台一致性审计。用户要求尽可能全面检查，不仅修复已有截图。

本轮不修改运行逻辑、不运行模型、不使用显卡。以下改动方向待逐批实现、测试、提交；不能把计划项目标成已交付。

## 基本约束

1. 服务端持久化的当前运行是权威来源；事件是通知，不是另一个独立真相。前端本地“请求中”与服务端“运行中”要分开。
2. 任务、一次运行、阶段、阶段内部进度、整体进度、输出版本分开表达；重试不是沿用上一轮未区分的事件。
3. 旧失败、旧完成、晚到工作线程及过期 HTTP 响应，不能覆盖新运行；界面也不能忽略真实的新失败。
4. 历史读改写须安全并发、原子落盘；完成状态与有效输出一致；不能吞掉损坏记录并悄悄当成空历史。
5. 字幕编辑、时间修正、人工确认必须持久化；源文、各语言译文、导出、配音和缓存使用一致的版本。
6. 先模拟和确定性时序测试，再浏览器、CPU 媒体验证，最后在用户同意释放 GPU 后实测。不得用“增加轮询/延长超时”代替根因修复。
7. 每批代码修改都补充测试并创建 Git commit。共享代码同步两版，收费版专有功能单独回归；保护所有用户资料。

## 已有证据与新增发现

原十项的证据仍以问题清单为准。以下是本轮扩大检查得到的新增最小验证，不代表均在目标机发生过。

### E01 渲染中重启恢复后仍被判定运行中

输入历史：status=pipeline_rendering、pipeline_status=processing、burn_status=processing。
`HistoryManager.recover_interrupted_tasks()` 仅把 burn_status 改成 failed，保留前两项；随后 `deriveTaskProcessingState` 仍返回 running=true、stage=render。

证据位置：`app/core/history.py`、`app/frontend/src/hooks/taskProcessingState.js`。需覆盖整套阶段组合，不只是把一个字符串加入列表。

### E02 新烧录失败被旧完成状态掩盖

输入：status=completed、pipeline_status=completed、burn_status=failed、burn_error=新错误。
当前前端恢复结果仍为 completed/100%。这是状态组合的最小复现；实际哪个操作留下这些字段，还需操作时序测试。

### E03 历史记录并发更新丢字段

用临时文件、两个受控线程，让两次 update_task 先读取同一历史，再依次写入：一次写 progress_percent，另一次写 burn_status。最终记录只保留后一次字段，前一次更新丢失。

证据位置：HistoryManager 的 update_task 是无锁的整个文件读改写。此验证只证明丢更新风险，不声称用户提供的 history 已因此损坏。后续还需覆盖任务创建/删除、不同任务、写入异常、损坏文件恢复与跨进程策略；单次 os.replace 不能单独解决丢更新。

## 分批实施顺序

### P1 状态与持久化基础：S01、S02，A01—A18

- 先将确认路径写成确定性失败测试；测试使用临时历史和假工作线程，不调用模型。
- 评估最小兼容的运行标识/单调状态版本；旧历史可读，不要求直接引入数据库或整体重写框架。
- 收敛状态更新与事件发布的顺序，补齐运行边界、操作互斥、并发写和启动恢复。
- 统一前端状态归约：同一份运行上下文驱动所有面板；避免多个 effect 各自决定终态。网络不可用要与任务失败区别显示。
- 为旧终态、晚到结果、单独烧录/配音错误、取消及重试提供可重复时序测试；已有有效输出不丢失。

出门条件：A01—A18 均有结论和测试/明确限制；实际修复的确定性用例及两版相关回归通过。若发现新风险，先记录再界定，不许声称当前已经全覆盖。

### P2 字幕编辑与加载可靠性：U03、U04

- 先修复空单元格可重新编辑、加载失败可见且可重试、过期请求不覆盖当前任务。
- 对真正新增/删除字幕行定义稳定行标识或可靠映射；源文、各语言译文、审核标记、时间、缓存引用同步更新，支持撤销。
- 编辑版本驱动后续输出失效；区别空行、加载失败、用户关闭源文和真实记录缺失，不默默清空文件。

出门条件：清空/恢复输入、刷新、网络失败恢复、切任务/切语言、插删行均保留正确数据；现有任务兼容。

### P3 时间轴自动处理：U08

- 先保留原始 ASR 及当前有效版本，之后新样本无需用户为了留现场再做一遍手工修改。
- 构建重叠分析：相邻小边界冲突、重复片段、嵌套/大范围重叠、乱序、真实并行对白分开统计。
- 确定安全规则后自动处理高置信项，汇总说明并可撤销；用户不需要逐条确认安全项。
- 对无法安全判断的片段给出定位与人工入口，不凭空裁短对白。预览与 ASS 渲染规则要一致，不能用预览 find() 隐藏多条有效字幕。
- 处理后的时间轴同步到所有译文和后续配音，按数据版本失效缓存。没有真实未改样本时先用合成边界样本，不把阈值臆定为已经可靠。

出门条件：所有时间有限、正时长、媒体内；正常边界不误改；无静默丢行/丢对白；自动安全项不再要求逐条修；撤销恢复原样；烧录与配音对齐验证通过。

### P4 人工审核与可恢复配音：U06、U07

- 用户已明确选择：每次翻译完成都暂停，手动继续。是否出现错位提示不影响暂停；在配音流水线中，确认后才进入后续配音/渲染。强制重译或精简生成新译文后也重新确认；单纯字幕翻译完成即停，不凭空启动配音。
- 审核绑定具体译文版本并持久化：已有译文未经确认时先展示确认入口；继续同一已确认版本不重复卡在等待点；编辑或重新生成导致版本变化时不得沿用旧确认。刷新/重启应恢复等待和明确的继续按钮。
- 两轮精简不足后保留问题行、分组映射、实测音长、超出量与已有语音，进入人工编辑等待，不直接丢掉问题上下文。
- 提供“保存后继续/确认继续/取消”等明确操作；继续前读取最新保存版本并重新测量，复用未改片段，不自动无限精简或截掉声音。
- 排查目标机 180 秒 TTS 超时与音色回退，先分清生成慢、进程卡死、失败清理和缓存行为；不直接延长超时或无提示换音色。

出门条件：刷新/重启可恢复待确认状态；继续幂等，不能同时启动两轮；真实失败仍被清楚显示；未修改仍不足时给明确人工指引。

### P5 渲染与播放：U02、U05、U01

- 字幕烧录打通输出策略 UI、预检、API、执行和持久化，复用适用的配音策略；纯字幕文件导出不转码。
- 媒体 seek 先检查目标包 Range 响应、媒体 duration/索引与实际 currentTime，再检查组件是否重挂载；不能先假设静态文件不支持 Range。
- 全屏统一容器/画面/字幕几何；分别测试 16:9、竖屏、超宽、缩放和退出恢复，区分控件位置与尺寸。

出门条件：输出参数与所选策略匹配；WAV/MP4 进度可拖动且不立即回跳；字幕、画面和控件在全屏中位置正确。

### P6 两版整体验收与累计补丁

- 先跑全量自动化和浏览器故障注入矩阵；再用目标视频/媒体做 CPU 可行项验证。
- 需要 GPU/TTS 长时间真实运行时提前通知用户，得到资源可用信息后再开始；目标物理机负责最终硬件验收。
- 每版交付一个清晰命名的累计补丁，包含此前仍需保留的修复，附文件清单、校验、适用基包、备份/回滚及验收步骤；不让用户反复猜补丁包含关系。
- 补丁之外，原完整 ZIP 是否重打单独说明；不顺带改变收费版打包范围或绕过既有再分发材料门槛。

出门条件：两版构建和全量测试通过；人工场景按清单记录；未复现/依赖目标机的项目明确保留，不以本机通过代替目标机验收。

## 交付节奏与非目标

- P1 优先交付可验证的状态基础修复，不等全部界面功能做完才让用户复测；每批都说明尚未覆盖项。
- P2 为 P3/P4 的人工编辑和数据版本提供基础；P3 为配音与渲染提供一致时间轴；P4 依赖 P1 的持久等待状态。
- 本轮不是实现授权扩大到发布上传、删除资料、升级 Tailwind、改变收费版组件范围或无预约占用 GPU。
- 有效检查范围不能保证穷尽所有并发时序；通过审计矩阵、可重复故障注入和后续日志补足证据，而不是承诺“不再出现任何不同步”。
